# Карта API для фронтенда

Первый этап реализует вход, профиль и учебный каталог. Всё через HTTP API, без серверных HTML-экранов.
В разработке машинный контракт доступен на `/openapi/v1.json`.
Карта соответствует текущим обработчикам API. Описанные ниже будущие маршруты пока нельзя вызывать.

## Связь с каркасом фронтенда

Фронтенд на HTML, CSS и JavaScript может работать с этим API; React для подключения не требуется.
Файлы в таблице — предложенное распределение работы по каркасу с доски, а не уже созданные файлы в этом репозитории.

| Файл фронтенда | Какие запросы использовать | Что учитывать |
|---|---|---|
| `api.js` | Все запросы `/api/*`, получение CSRF-токена | Общая обработка cookie, CSRF и ошибок; вход не выдаёт Bearer-токен |
| `main.js` | `GET /api/me`, затем `GET /api/courses` | При запуске восстановить профиль через API; `401` означает необходимость входа |
| `router.js` | Сам по себе запросов не требует | Управляет экранами клиента. Адрес экрана профиля не обязан совпадать с `/api/me` |
| `state.js` | Получает данные от `api.js` | Хранит состояние интерфейса. XP, монеты и отметки чтения приходят с сервера; клиент их самостоятельно не начисляет |
| Экран регистрации и входа, например `views/auth.js` | `/api/auth/csrf`, `/api/auth/register`, `/api/auth/login`, `/api/auth/logout` | После регистрации отдельно выполнить вход; после входа или выхода обновить CSRF-токен |
| `views/profile.js` | `GET /api/me` | Сейчас доступны никнейм, ключ аватара, общее XP и монеты. Разряда и порогов для полосы XP нет |
| Главная страница | `GET /api/me`, `GET /api/courses`, `GET /api/courses/{courseId}/topics` | Можно показать профиль и список тем. Процент прохождения курса и ближайшие темы API пока не вычисляет |
| `views/theory.js` | `GET /api/courses/{courseId}/topics`, `GET /api/topics/{topicId}`, `GET /api/lessons/{lessonId}`, `PUT /api/me/lessons/{lessonId}/completion` | Лекцию отображать из `contentMarkdown`; отметка чтения сохраняется отдельно |
| `views/battle.js` | Пока нет работающих маршрутов боя | Модели проверки и попытки есть, но старт, ответы, таймер, результат и награды ещё не реализованы |

В изображении файл глобального состояния назван `stake.js`. Если речь о состоянии интерфейса,
обычное название — `state.js`; на API это имя не влияет.

## Реализовано

| Метод | Путь | Вход | Результат |
|---|---|---|---|
| GET | `/api/auth/csrf` | Нет | `token`, `headerName`; устанавливает CSRF-cookie |
| POST | `/api/auth/register` | CSRF | Создаёт пользователя и профиль атомарно; 201 |
| POST | `/api/auth/login` | CSRF | Устанавливает auth-cookie; 204 |
| POST | `/api/auth/logout` | Cookie + CSRF | Выход; 204 |
| GET | `/api/me` | Cookie | Собственный профиль, XP и монеты |
| GET | `/api/courses` | Cookie | Опубликованные курсы |
| GET | `/api/courses/{courseId}/topics` | Cookie | Темы и количество прочитанных лекций |
| GET | `/api/topics/{topicId}` | Cookie | Тема, список лекций, метаданные опубликованных проверок |
| GET | `/api/lessons/{lessonId}` | Cookie | Markdown лекции и собственная отметка чтения |
| PUT | `/api/me/lessons/{lessonId}/completion` | Cookie + CSRF | Одна отметка чтения; повтор возвращает прежнюю дату |
| GET | `/health/live` | Нет | Работает ли процесс |
| GET | `/health/ready` | Нет | Доступна ли БД и применены ли миграции |

Тела запросов:

`POST /api/auth/register`:

```json
{"email":"student@example.test","password":"Development123!","displayName":"Студент"}
```

`POST /api/auth/login`:

```json
{"email":"student@example.test","password":"Development123!"}
```

Это примеры для локального теста, а не встроенный аккаунт. Для отметки чтения тело не используется;
можно отправить `{}`. Отметка не является проверкой знаний и не выдаёт награду.

`GET /api/me`:

```json
{
  "userId":"00000000-0000-4000-8000-000000000001",
  "displayName":"Студент",
  "avatarKey":"default",
  "totalXp":0,
  "coinsBalance":0
}
```

Пороговые значения уровня и разряда ещё не согласованы, поэтому эти вычисляемые поля пока не добавлены.
Метаданные проверки содержат только `id`, `title`, `mode`, `isRequired`; вопросы и ответы не выдаются.
В демо-данных первого этапа проверок пока нет.

## Данные для экранов

Ответы сериализуются в JSON с именами полей в `camelCase`. UUID передаются строками,
даты — строками ISO 8601 с часовым поясом. Успешные вход и выход возвращают `204` без тела;
для таких ответов нельзя безусловно вызывать `response.json()`.

| Запрос | Форма успешного ответа |
|---|---|
| `GET /api/auth/csrf` | Объект: `token`, `headerName` |
| `POST /api/auth/register` | Объект: `userId`, `email`; статус `201`. Регистрация не устанавливает auth-cookie |
| `GET /api/me` | Объект: `userId`, `displayName`, `avatarKey`, `totalXp`, `coinsBalance` |
| `GET /api/courses` | Массив объектов: `id`, `slug`, `title`, `description` |
| `GET /api/courses/{courseId}/topics` | Массив объектов: `id`, `title`, `description`, `sortOrder`, `lessonCount`, `completedLessons` |
| `GET /api/topics/{topicId}` | Объект: `id`, `courseId`, `title`, `description`, `lessons`, `assessments` |
| `GET /api/lessons/{lessonId}` | Объект: `id`, `topicId`, `title`, `contentMarkdown`, `completedAt` |
| `PUT /api/me/lessons/{lessonId}/completion` | Объект: `lessonId`, `completedAt`; статус `200`, в том числе при повторе |

Элемент `lessons` в теме содержит `id`, `title`, `sortOrder`.
Элемент `assessments` содержит `id`, `title`, `mode`, `isRequired`.
`mode` сериализуется строкой: `Boss` или `Crisis`. Наличие этого поля не означает готовность соответствующего режима.

`completedAt = null` означает, что текущий пользователь ещё не отметил лекцию прочитанной.
`completedLessons` — количество прочитанных опубликованных лекций в теме, а не количество побед.
Даже если оно равно `lessonCount`, тему нельзя считать пройденной по правилам MVP: для этого нужна победа в проверке.
Статусы `locked`, `available`, `completed`, разряд, пороги XP и процент курса сейчас в ответах отсутствуют.
Все опубликованные темы доступны авторизованному пользователю без последовательного открытия.

`avatarKey` — ключ оформления, а не URL изображения. Значение `default` фронтенд сопоставляет со своим ресурсом.
Начальные `totalXp` и `coinsBalance` равны нулю. Отметка чтения их не изменяет.

Содержание лекции хранится в Markdown. Отображение текста, формул и ссылок на изображения выполняет фронтенд;
загрузка файлов и изображений через API пока не предусмотрена.

## Как подключить `api.js`

### Адрес API и cookie

Локальный адрес бэкенда — `http://localhost:5244`. В браузере использовать относительные пути `/api/...`.
Фронтенд должен открываться через HTTP-сервер; открытие `index.html` через `file://` не является настроенной интеграцией.

Если фронтенд запускается на другом порту, настроить у его сервера разработки прокси `/api`
на `http://localhost:5244`. Браузер при этом обращается к своему origin. При публикации аналогично
размещать UI и `/api` на одном origin через обратный прокси.
CORS для прямых запросов с другого origin в приложении пока не настроен;
одного `credentials: "include"` для такой схемы недостаточно.

Для запросов через общий origin можно явно указывать `credentials: "same-origin"`.
Браузер сохраняет и отправляет auth-cookie; JavaScript не читает её, поскольку она `HttpOnly`.
JWT или пароль сохранять в `localStorage` для текущей схемы входа не требуется.

### Порядок регистрации и входа

1. Получить `GET /api/auth/csrf` и сохранить `token` в памяти клиента.
2. Отправить регистрацию с JSON `{ "email": "...", "password": "...", "displayName": "..." }`
   и заголовком `X-CSRF-TOKEN`.
3. После успешной регистрации отдельно отправить вход с JSON `{ "email": "...", "password": "..." }`
   и тем же актуальным CSRF-токеном. При обычном входе шаг регистрации пропускается.
4. После `204` от входа снова получить `/api/auth/csrf`: токен должен соответствовать вошедшему пользователю.
5. Получить `/api/me` и каталог. По этим ответам заполнить состояние интерфейса.
6. Для отметки чтения использовать `PUT /api/me/lessons/{lessonId}/completion` с CSRF-заголовком;
   тело можно не отправлять или передать `{}`.
7. Для выхода использовать `POST /api/auth/logout` с актуальным CSRF-токеном;
   затем очистить состояние пользователя и получить новый токен перед следующим входом.

CSRF обязателен для всех изменяющих запросов под `/api`, включая регистрацию и вход.
Не отправлять в операции чтения ID пользователя: API определяет его по cookie.

Пример подключения из JavaScript после настройки общего origin или прокси:

```javascript
let csrfToken;

async function refreshCsrf() {
  const response = await fetch("/api/auth/csrf", { credentials: "same-origin" });
  if (!response.ok) throw new Error("Не удалось получить CSRF-токен");
  csrfToken = (await response.json()).token;
}

async function login(email, password) {
  await refreshCsrf();
  const response = await fetch("/api/auth/login", {
    method: "POST",
    credentials: "same-origin",
    headers: {
      "Content-Type": "application/json",
      "X-CSRF-TOKEN": csrfToken,
    },
    body: JSON.stringify({ email, password }),
  });
  if (!response.ok) throw await response.json();
  // У входа статус 204: JSON-тела нет.
  await refreshCsrf();
  const profile = await fetch("/api/me", { credentials: "same-origin" });
  if (!profile.ok) throw await profile.json();
  return profile.json();
}
```

### Проверка данных и ошибки

- Регистрация: корректный email длиной до 256 символов, `displayName` после удаления пробелов по краям
  длиной 1–80 символов. Пароль — 10–128 символов, с цифрой, строчной и прописной буквами;
  спецсимвол необязателен. Уникальность никнейма не требуется; email уникален без учёта регистра.
- `400`: ошибка данных или CSRF. Ошибки валидации содержат словарь `errors`;
  ошибка CSRF содержит `code: "InvalidCsrfToken"`.
- `401`: неверные данные входа или отсутствие действующего входа для защищённого маршрута.
  В первом случае показать ошибку формы, во втором — перейти к экрану входа.
- `403`: недостаточно полномочий.
- `404`: материал не существует или недоступен, в том числе не опубликован.
- Повторный email при регистрации обычно возвращает `400` с ошибкой Identity;
  при конфликте одновременных регистраций возможен `409`.
- Ошибки API используют `ProblemDetails` / `ValidationProblemDetails`. Стабильный машинный `code`
  пока есть у ошибки CSRF, но не у каждой ошибки; не строить всю обработку только на этом поле.

### Проверка подключения фронтенда

После миграции и загрузки демо-данных пройти цепочку: регистрация → вход → профиль → список курсов
→ темы → лекция → отметка чтения → обновление страницы → повторный вход.
Отметка чтения должна сохраниться, а повторный запрос — вернуть прежний `completedAt`.
Для другого пользователя эта лекция должна оставаться непрочитанной.

В демо-данных:

- `courseId`: `10000000-0000-4000-8000-000000000001`;
- `topicId`: `20000000-0000-4000-8000-000000000001`;
- `lessonId`: `30000000-0000-4000-8000-000000000001`.

Это значения для локальной проверки. В интерфейсе получать ID из ответов API.

## Следующий этап — пока не реализован

| Метод | Путь | Операция |
|---|---|---|
| POST | `/api/assessments/{assessmentId}/attempts` | Создать/вернуть активную попытку |
| GET | `/api/attempts/{attemptId}` | Получить состояние и текущий вопрос |
| PUT | `/api/attempts/{attemptId}/questions/{attemptQuestionId}/answer` | Принять один ответ и перейти дальше |
| POST | `/api/attempts/{attemptId}/abandon` | Завершить попытку без победы |
| GET | `/api/attempts/{attemptId}/result` | Итог и фактически начисленная награда |
| GET | `/api/me/attempts` | История с пагинацией |

Эти маршруты не зарегистрированы в приложении; они описывают направление разработки.
Административное редактирование материалов, публикация проверок и почтовое восстановление
доступа также реализуются отдельным этапом после уточнения требований.

Правила следующего этапа: проверка владельца, неизменяемая версия задания,
дедлайн по серверному времени, идемпотентный ответ, результат и награда в одной транзакции.

Для `views/battle.js` ещё предстоит согласовать DTO текущего вопроса, шага ответа и итогов.
Босс-тест должен учитывать требования MVP: 7 вопросов, победа при 5 верных,
урон 20% HP за верный ответ, поражение на третьей ошибке, таймер 45–60 секунд и случайный выбор из банка.
Расчётный ответ с числом пока не поддержан текущим типом `SingleChoice`.
QTE с изменением времени и нагрузки требует отдельного контракта состояния сценария;
перечисленных будущих маршрутов попыток недостаточно, чтобы считать этот режим спроектированным.
После реализации наград нужно дополнить `/api/me` разрядом и данными для полосы XP,
а каталог — статусами тем и процентом прохождения курса.
